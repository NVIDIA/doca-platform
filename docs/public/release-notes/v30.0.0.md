---
title: "DOCA Platform Framework v30.0.0"
---

This is the GA release of the DOCA Platform Framework (DPF). It includes bug fixes
and improvements to enhance the provisioning and orchestration of NVIDIA BlueField
DPUs in Kubernetes environments.

### Revision History

| Date            | Description                                                            |
|-----------------|------------------------------------------------------------------------|
| November 2026   | General Availability (GA) release of DOCA Platform Framework v30.0.0   |

### Features

* **In-place DPU reconfiguration**
    * A new CRD and flow reconfigure a provisioned DPU without reprovisioning it. A round is started
      from an annotation on the `DPUSet`, runs the DPU through Node Effect to DPU Config and re-runs the
      DPU agent when the phase returns to DPU Config.
    * The DPU agent fetches the live `DPUFlavor`, so flavor changes are picked up during a round.
    * A round respects `maxUnavailableDPUNodes`.

* **Consolidated PKI**
    * The provisioning CA is collapsed into the platform CA, and the provisioning leaves are signed by
      the platform CA.
    * The platform CA can be anchored in a configurable issuer and rotated without a pin. The trust
      bundle is left to whoever owns the CA.
    * The webhook certificates chain to a single DPF root CA.
    * See the documentation on switching to your own authority and on rotating a self-signed CA.

* **SPIFFE workload identity**
    * Builds on the SPIFFE identity introduced in [v26.8.0](./v26.8.0.md). The SPIFFE CSI driver can
      be deployed to DPU clusters and its images can be overridden.
    * DPUServices can opt in to register SPIFFE workload identities, and the DPU agent identities are
      templated and restricted with hardened selectors.
    * Kubernetes workload attestation is enabled on the DPUs that use SPIFFE.
    * A DSX SPIFFE Helper is available.
    * **Limits:**
        * SPIFFE is opt-in through `DPFOperatorConfig.spec.security.spiffe` and needs a pre-installed
          SPIRE deployment. Nothing changes on upgrade unless it is enabled.
        * It is available in Zero Trust deployments only.
        * It applies to newly provisioned DPUs only. Existing DPUs stay in bootstrap-token mode even
          after SPIFFE is enabled, and a cluster can hold a mix of both. DPF skips bootstrap-token
          DPUs when registering DPUService identities, so DPUServices on those DPUs do not receive
          one until the DPU is reprovisioned.
    * For setup, see [SPIFFE Workload Identity](../advanced-configuration/spiffe-identity.md).

* **DPUFlavor**
    * `spec.scalableFunctions` and `spec.virtualFunctions` declare SR-IOV function groups, and
      `spec.dma.enabled` enables the DMA SF. The DPU agent creates the functions and generates the
      configuration of the SR-IOV device plugin.
    * The container sandbox image can be overridden and the immutability of a `DPUFlavor` is enforced
      per field.
    * See the guide for configuring DPU Virtual Functions.

* **DPU provisioning**
    * Fewer reboots in the DPU provisioning flows.
    * DPU provisioning is held while a DPF upgrade is in progress.
    * A new service readiness phase gates the DPU on the readiness of its DPUServices.
    * BMC hardening: factory reset and password hardening, rotation of the BMC server certificate and
      mTLS is re-established when the BMC IP of a `DPUDevice` changes.
    * Firmware: PLDM firmware bundles per PSID, recovery of BlueField-4 PLDM updates and an annotation
      to force a firmware update.
    * The DPU Arm boot progress is reported in Zero Trust while the OS is installing, and the host
      clock is adopted over tmfifo in Host Trusted mode.
    * The DPU controller supports opt-in concurrent workers.

* **Networking and service chaining**
    * IPv6 IPAM, including the IPAM API.
    * `ServiceInterfaceSet` objects are migrated to `NodeServiceInterfaces` on reconcile, and
      `NSIPathForSFC` is enabled by default.
    * A new link-state-propagation service.
    * The DPU cluster DNS is served from the host cluster, and the standard CNI plugins are installed
      on the DPU.

* **Storage**
    * A CMX initiator DPUService component.
    * MEMOS KV volumes are exposed on SNAP, and each SNAP volume gets its own NVMe subsystem.
    * IPv6 NVMe targets are supported.

* **Distributed tracing with OpenTelemetry**
    * DPF controllers export trace spans for their reconcile loops. One change of a top-level object,
      such as a `DPUDeployment`, is one trace that joins the reconciles of the object and of
      everything it creates.
    * An upstream caller can set the `tracing.k8s.io/traceparent` and `tracing.k8s.io/tracestate`
      annotations on the objects it creates, so a single request can be followed across the DPF
      controllers. Without them DPF derives the trace from the UID and generation of the object.
    * The orchestration, provisioning (including Redfish HTTP calls) and SDN controllers
      (`sfc-controller`, `pod-ipam-injector`) are instrumented.
    * Tracing is disabled by default. `DPFOperatorConfig.spec.monitoring.tracing.otlp.endpoint` is the
      destination of the controllers in the Host Cluster and
      `spec.monitoring.openTelemetryCollector.tracing.endpoint` the destination of the DPU clusters.
      A Tempo backend is supported.
    * See [Tracing](../operational-readiness/observability/deployment/operator-managed-components.md#tracing)
      for the configuration and for how to set the trace context.

* **DPU OpenTelemetry collector**
    * The collector accepts a full custom configuration and TLS endpoints.
    * Only the signals that have an endpoint configured are exported.
    * The Services of the `opentelemetry-collector` and `node-problem-detector` DPUServices in the DPU
      clusters are named after the DPUService, so the name is the same in every DPU cluster.

* **DPFOperatorConfig**
    * The default DaemonSet `maxUnavailable` is configurable.
    * Usage of deprecated fields is reported in the status.
    * `deploymentMode` is immutable after creation.

* **Air gap**
    * Tooling, a SOCKS proxy guide and a bill of materials for air-gapped installations.

* **Platform**
    * The DPUCluster Kubernetes version is bumped to v1.36.5.
    * Blueman is no longer supported by DPF.

### Fixed Issues from Previous Release

* **Stale ports after DPU reboot**
    * Stale OVS ports are deleted by UUID instead of by name, so a leftover port no longer causes
      duplicated traffic after a DPU reboot or power cycle.
    * Internal Ref #4174183, #5361112

* **[Zero Trust] Manual change of DPU mode from DPU to NIC after DPU discovery causes provisioning to
  stall in Rebooting**
    * Provisioning no longer remains stuck in the `Rebooting` phase after the DPU mode was changed
      manually after discovery.
    * Internal Ref #4984034

* **OS installation failure after a leader switch of the provisioning controller (Zero Trust)**
    * In Zero Trust, the `bfb-registry` host and NodePort that are baked into the DPU configuration
      stay stable across a leader failover of the provisioning controller or an upgrade, so DPU OS
      downloads keep passing TLS verification. This is still a known issue for Host Trusted
      deployments.
    * Internal Ref #4957820

* **BMC account lockout**
    * The password from the secret is tried before falling back, which avoids locking the account.

* **Security**
    * CVE fixes in the Go toolchain, nginx, gRPC, oras-go, x/mod, x/text, the attacher etcd client
      (GO-2026-6107) and the VPC components.

### Supported DPU Services

The support status of each service is unchanged compared to

* The CMX initiator and the link-state-propagation service are new.

### Installation & Upgrade Notes

#### Installation Notes

None.

#### Upgrade Notes

* Existing `DPUFlavor` objects keep working. Flavors without function groups still derive their
  Scalable Functions from `PF_TOTAL_SF` and the trusted SF annotation.
* DPU provisioning is held while the upgrade is in progress, so new DPUs start provisioning once the
  upgrade completes.
* In the DPU clusters, the Services of the OpenTelemetry collector and node-problem-detector are
  renamed from `<dpucluster>-opentelemetry-collector` and `<dpucluster>-node-problem-detector` to
  `opentelemetry-collector` and `node-problem-detector`. The old Services are deleted during the
  upgrade and are not kept for compatibility. Clients in the DPU clusters that reach these Services by
  name, such as a custom collector or a Prometheus scrape configuration, must use the new name.

### Known Issues and Limitations

* **Socket Direct environments are not supported**
    * DPF does not currently support environments where NVIDIA Mellanox [Socket Direct](https://www.nvidia.com/en-us/networking/ethernet/socket-direct/) adapters are used. Socket Direct is a network adapter architecture that provides direct PCIe access from multiple CPU sockets to a single NIC, bypassing the inter-processor bus. DPUs in Socket Direct configurations are not tested or validated with DPF.
    * For more details, see [Platform Support - Limitations](../platform-support.md#limitations).

* **DPU Cluster control-plane connectivity is lost when physical port P0 is down on the worker node**
    * Link down of p0 port on the DPU will result in DPU control plane connectivity loss of DPU components.
    * Internal Ref #3751863
    * **Workaround:** Make sure P0 link is up on the DPU, if down either restart DPU or refer to DOCA
      troubleshooting https://docs.nvidia.com/networking/display/bfswtroubleshooting.
      **Note:** This issue is relevant for Host Trusted deployments only.

* **System doesn't recover after DPU Reset**
    * When the user triggers a reset of a DPU in any way other than using DPF APIs (e.g. recreation of a DPU CR),
      the system may not recover.
    * Internal Ref #4521178, #4732664
    * **Workaround:** Power cycle the host. Note that this operation is dangerous and there might be file system
      corruption which will require triggering the reprovisioning of the DPU. If the system does not recover,
      reprovision the DPU by deleting the DPU CR (it will be recreated and DPU provisioning will happen).
      **Note:** This issue is relevant for Host Trusted deployments where OVN-Kubernetes is used as a primary CNI.

* **Leftover CRs if worker is removed from the cluster permanently**
    * When a worker was added to a cluster, optionally had DPU provisioned and later was removed from the host cluster
      permanently, there may be leftover DPF related CRs in both the host cluster and the DPU cluster.
    * Internal Ref #4403130
    * **Workaround:** No workaround, known issue.

* **DPUService stops reconciling when DPUCluster is unavailable for long time**
    * When the DPUCluster is unavailable for long time (more than 5 mins), changes to DPUServices (also generated ones
      via DPUDeployment or DPFOperatorConfig) that have happened during that time might not be reflected to the
      DPUCluster.
    * Internal Ref #4359857
    * **Workaround:** Recreate DPUServices that are stuck.

* **[OVN-Kubernetes DPUService] Lost traffic from workloads to control plane components or Kubernetes services after dpu reboot, port flapping, ovs restart or manual network configuration**
    * Connectivity issues between workload pods to control plane components or Kubernetes services may occur
      after the following events: DPU reboot without host reboot, high speed port flapping (link down/up), ovs restart,
      DPU network configuration change (for example using "netplan apply" command on DPU).
      The issues are caused by network configuration that was applied by ovn CNI on DPUs and won't get reapplied
      automatically.
    * Internal Ref #4521178
    * **Workaround:** Recreate the OVN-Kubernetes node pod on the host to reapply the configuration.

* **[OVN-Kubernetes DPUService] No network connectivity for SR-IOV accelerated workload pods after DPU reboot**
    * SR-IOV accelerated workload pod is losing its VF interface upon DPU reboot. VF is available on the host however
      not injected back into the pod.
    * Internal Ref #4236521
    * **Workaround:** Recreate the SR-IOV accelerated workload pods.

* **[Firefly DPUService] Deletion of the Firefly DPUService leaves stale flows in OVS**
    * When the Firefly DPUService is deleted after successful deployment or the labels of the serviceDaemonSet are
      modified, flows are not cleaned up from OVS.
    * Internal Ref #4382535
    * **Workaround:** Although these flows are very unlikely to cause an issue, reprovisioning the DPU or power cycling
      the host will bring the OVS in good state. Note that power cycling the host is dangerous and there might be file
      system corruption which will require triggering the reprovisioning of the DPU.

* **[DPUDeployment] Pods of service referenced in spec.serviceChain are restarted when serviceChain changes, causing disruption**
    * When updating DPUDeployment.spec.serviceChain with a disruptive upgrade, the affected pods are restarted but DPUDeployment
      removes the node effect from the corev1.Node in the host cluster proactively.
      This causes the node to be marked as ready and accept workloads before DPU services are fully operational.
    * Internal Ref: #4686635
    * **Workaround:** No workaround, known issue.

* **Long DPU provisioning time when multiple DPUs are provisioned on the same node**
    * In some cases, it may take a long amount of time to provision multiple DPUs on the same node.
    * Internal Ref: #4757191
    * **Workaround:** If the DPU is stuck in `DPU Cluster Config` phase after a long installation, please reprovision the DPU and make sure no other DPUs on the same node are being provisioned at the same time

* **[DPUDeployment] DPU does not recover to Ready after Node Effect Removal timeout, even when service configuration is reverted**
    * When a DPUDeployment is deployed and becomes ready, and then a service is updated with an invalid configuration
      (e.g. overriding the image with a wrong one in DPUServiceConfiguration), the DPU enters the Node Effect Removal
      state. If the Node Effect Removal timeout is exceeded, the DPU transitions to Error state. Even after reverting
      the DPUServiceConfiguration to the previous valid configuration, the DPU does not move back to Ready.
      The `nodeEffectRemovalTimeout` in `DPFOperatorConfig.spec.provisioningController` defaults to `0s` (disabled), meaning this issue will not occur with the default configuration. If the timeout is explicitly set to a non-zero value (e.g. `30m`), ensure the configured duration allows sufficient time for configuration corrections before the DPU transitions to Error state.
    * Internal Ref: #4952676
    * **Workaround:** Revert to a working configuration and delete the DPU CR to trigger reprovisioning.

* **Leader switch of the provisioning controller pod while the DPU is in the middle of deploying may cause OS installation failure (Host Trusted)**
    * When deploying a DPU without `bfbPVCName` provided in the DPFOperatorConfig, a leader switch in the DPU provisioning controller (for any reason)
      during the provisioning process may cause the DPU to transition to the `Error` phase due to download failures of the BFB or bfb.cfg during OS installing.
      This issue produces an `OSInstalled` condition (`InstallationTerminated` reason) in the host-trusted environment.
      It is fixed for Zero Trust deployments.
    * Internal Ref: #4957820
    * **Workaround:** Delete the DPU CR to trigger reprovisioning.

* **DOCA SNAP may fail to reattach a DPUVolumeAttachment that uses VirtioFS or emulated NVMe devices on hot-plugged PFs after a host power cycle**
    * After a host power cycle, a DPUVolumeAttachment that uses VirtioFS or emulated NVMe devices on hot-plugged PFs can become not ready and might not be restored automatically.
    * Internal Ref: #4734537
    * **Workaround:**
        * **Step 1:** Delete failed DPUVolumeAttachment.
        * **Step 2:** Create a new DPUVolumeAttachment with the same configuration.

* **DPU can remain stuck in DPU Config when a DPUFlavor adds a ConfigMap during OS installation**
    * If a DPU has passed `Prepare BFB` and its `DPUFlavor` is updated during OS installation with
      an agent-applied `configFiles` entry that references a new ConfigMap, the DPU agent reads the
      updated flavor but its Role is not refreshed with permission to read that ConfigMap. The read
      is rejected as forbidden, the agent does not report a reboot method, and the DPU remains in
      `DPU Config` with the `DPUConfig=False` condition and `WaitingForRebootMethod` reason.
    * Internal Ref: #5409290
    * **Workaround:** Add all agent-applied ConfigMap references to the `DPUFlavor` before the DPU
      enters OS installation. If a DPU is already affected, add the ConfigMap name to the
      `resourceNames` of the corresponding `da-<dpu-name>` Role so that the next DPU agent retry can
      continue. Alternatively, reprovision the DPU after finalizing the flavor.
