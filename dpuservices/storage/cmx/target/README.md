# CMX target DPUService

DPF manifests that deploy the CMX target (`doca-cmx-target`) as a DPUService.

The files are generated by the cmx-target CI (`.ci/build_dpf.py`) from the
Jinja2 templates in the cmx-target repository. Apart from the chart repository
placeholder described below, they are not meant to be edited by hand; changes
belong in those templates, and this directory is refreshed from the next drop.

Chart version: `1.0.0-6`.

## Files

| File | Purpose |
| --- | --- |
| `DPUService.yaml` | Installs the `doca-cmx-target` Helm chart on the DPUs. The container image is baked into the chart, so the CR does not name it. |
| `DPUObjects.yaml` | SFC networking the service attaches to: `DPUServiceNAD`, two `DPUServiceIPAM` pools, the `p0`/`p1` uplink and `net1`/`net2` service `DPUServiceInterface`s, and the `DPUServiceChain`. |
| `DPUFlavor.yaml` | DPU provisioning flavor: kernel arguments (including hugepages), NV config and OVS setup. For DPUs whose OS uses 64KB kernel pages only (see [Deploying](#deploying)). |

`DPUService.yaml` and `DPUObjects.yaml` must be applied together: the service
declares the interfaces that `DPUObjects.yaml` defines, and the objects have no
service to connect without it. `DPUFlavor.yaml` is referenced by the DPUs'
provisioning and is applied separately.

All objects are created in the `dpf-operator-system` namespace.

## Scoping to specific DPUs

The manifests carry no node selectors apart from `p1` (see below), so as shipped
they apply to every DPU node in the DPU cluster. A `DPUSet` or `DPUDeployment`
selector does not change this: it only scopes the objects that deployment itself
creates, not objects applied separately like these. To restrict the CMX target
to some DPUs, set the selector on each object (the DPU node labels are those of
your DPU cluster):

| Object | Field | Type |
| --- | --- | --- |
| `DPUService` | `spec.serviceDaemonSet.nodeSelector` | `NodeSelector` (`nodeSelectorTerms`) |
| `DPUServiceIPAM` (both pools) | `spec.nodeSelector` | `NodeSelector` (`nodeSelectorTerms`) |
| `DPUServiceInterface` (`p0`, `p1`, `net1`, `net2`) | `spec.template.spec.nodeSelector` | label selector (`matchLabels`) |
| `DPUServiceChain` | `spec.template.spec.nodeSelector` | label selector (`matchLabels`) |

`p1` carries `kubernetes.io/os: linux`, like the `p1` of the storage SNAP examples,
so applying both does not make the two definitions overwrite each other. It
matches every DPU node; narrow it together with the other selectors if you scope.

`DPUServiceNAD` has no node selector. Use the same label match on all of the
objects above; if the interfaces or the chain are scoped more widely than the
service, they are created on DPUs where the service does not run.

Because the files are generated, add the selectors in the cmx-target templates
if they should be part of the drop, or as a local patch (for example with
`kustomize`) when applying.

## Helm chart

The chart itself is not stored in this repository, and it is not published to a
public Helm repository yet. `DPUService.yaml` therefore carries the placeholder
`repoURL: https://$DPUSERVICE_HELM_REGISTRY`, as the `dummydpuservice` example
does; it is not expanded by `kubectl apply`. Replace it, for example with
`envsubst`, with the Helm repository that hosts the `doca-cmx-target` chart
before applying. Once the chart is published, the placeholder will be replaced by
its public location.

## Deploying

The files are examples: they need the changes below before they work in your
cluster. Do them from top to bottom.

* **Set the chart repository.** In `DPUService.yaml`, replace
   `https://$DPUSERVICE_HELM_REGISTRY` with the Helm repository that hosts the
   `doca-cmx-target` chart (see [Helm chart](#helm-chart)). The value must start
   with `oci://` or `https://`, so for an OCI registry replace the whole value,
   scheme included. Do not pass the other files through `envsubst`:
   `DPUFlavor.yaml` contains a literal `"$@"`.
* **Set the IP addressing.** In `DPUObjects.yaml`, change the subnet and gateway
   of both `DPUServiceIPAM` pools (`10.44.44.0/24` and `10.44.45.0/24` are example
   addressing for the `p0`/`p1` RDMA fabric, not a usable default) and make
   `perNodeIPCount` large enough for your DPUs.
* **Decide where it runs.** With no changes the objects apply to every DPU node.
   To restrict them, set the same node selector on every object listed in
   [Scoping to specific DPUs](#scoping-to-specific-dpus).
   `DPUObjects.yaml` defines its own `DPUServiceChain` (`cmx-target`) with the
   `p0`/`p1` uplinks. As shipped it is the only chain. If the same DPUs also run
   another chain that uses an uplink (for example the storage `spdk-chain` or
   `hbn`), two chains on the same uplink install conflicting flows. In that case
   adjust the objects: scope them to different DPUs with node selectors, or add
   the `net1`/`net2` ports to the existing chain instead of applying
   `cmx-target`.
* **Leave the shared names alone.** Keep `p0` and `p1` and their `uplink` labels
   (`hbn` and the SNAP examples select the uplinks by them). Keep the
   `DPUServiceNAD` name `mybrsfc-storage` if DOCA SNAP also runs in the cluster:
   it is identical to the one in the storage examples, so both converge on a
   single NAD on the `br-sfc` bridge. Change it only if you also change it
   everywhere it is referenced (the `network` of `net1`/`net2`).
* **Review `DPUFlavor.yaml`.** Check the kernel arguments, NV config, OVS setup
   and hugepages against the DPU provisioning you use before referencing it from
   there. The flavor is for DPUs whose OS uses a 64KB kernel page size
   (`getconf PAGESIZE` prints `65536` on the DPU). Its NV config (`PF_SF_BAR_SIZE=10`,
   `BAR_PAGE_ALIGNMENT=2`) and its hugepages (`hugepagesz=512M hugepages=16`, that
   is 16 pages of 512 MiB for 8 GiB) are the values for that page size. It does not
   support a DPU OS with 4KB pages, and no 4KB variant is provided here.
   The hugepages are reserved with kernel parameters, as in the other DPF flavors,
   so they exist before kubelet starts. The flavor also reserves 250 pages of
   2 MiB (`hugepagesz=2048kB hugepages=250`, 500 MiB) for OVS-DOCA, which it enables
   with `OVS_DOCA="yes"`. It does not use `doca-hugepages`: the tool refuses to run
   once hugepage kernel parameters are set, so the OVS-DOCA pool has to come from
   the kernel parameters too. Size the 2 MiB pool for your OVS-DOCA use.
   Alternatively, you can reserve the hugepages with `doca-hugepages` instead of
   kernel parameters. The two methods are mutually exclusive: remove all four
   `hugepagesz`/`hugepages` kernel parameters from `DPUFlavor.yaml` first, because
   the tool refuses to run when hugepages are configured through GRUB. Then, on
   the DPU, as root:

   ```bash
   doca-hugepages config --app doca_cmx_target --size 524288 --num 16 --force
   doca-hugepages reload
   ```

   The configuration is stored in `/etc/mellanox/hugepages.d/` and restored at
   every boot. With `OVS_DOCA="yes"` the BlueField boot configuration reserves the
   2 MiB pool for OVS-DOCA through the same tool, so it does not need to be
   configured separately. The pool is allocated after the DPU has booted, so it
   may not exist yet when kubelet starts; kubelet can then report no hugepages
   until it is restarted, and the CMX target pod stays Pending with
   `Insufficient hugepages-512Mi`. The kernel parameters avoid this.
   The flavor also sets `mtu_request=9000` on `p0` and `p1` (the Ethernet MTU).
   Keep it above the RDMA MTU, which is 4096 by default: if the Ethernet MTU
   falls back to 1500, RDMA with a 4096 MTU does not work. Do not drop it or set
   it below 4096. 9000 is a good default, but the right value is data center
   specific, so you can customize it, as long as it stays above the RDMA MTU.
   `FORCE_DPU_CONFIGURE="yes"` in `mlnx-bf.conf` enables the full BlueField
   configuration for JBOF platforms; keep it on a JBOF, and drop it only if the
   DPU is not one.
   The two SFs for `net1`/`net2` are declared with `scalableFunctions` (`count: 2`,
   `device: "*"`, `poolName: bf_sf`), matching `PF_TOTAL_SF=2` in the NV config.
   The `scalableFunctions` field requires a DPF version that has it (v30.0.0 and
   later); on an older DPF version remove the block, and the SFs are sized from
   `PF_TOTAL_SF` instead.
* **Apply.** `DPUService.yaml` and `DPUObjects.yaml` together, in the
   `dpf-operator-system` namespace:

   ```bash
   kubectl apply -f DPUObjects.yaml -f DPUService.yaml
   ```

   `DPUFlavor.yaml` is applied separately.
* **Check.** The `DPUService` `doca-cmx-target` becomes ready, and the
   `DPUServiceInterface`s (`net1`, `net2`) and the `DPUServiceChain`
   `cmx-target` are created on the intended DPUs. You can check this using either
   [dpfctl](../../../../docs/public/operational-readiness/troubleshooting/dpfctl/README.md)
   or kubectl:

   **Using dpfctl (recommended):**

   ```bash
   dpfctl describe all --show-resources=dpuservice/doca-cmx-target --show-conditions=all
   ```

   **Using kubectl:**

   ```bash
   kubectl -n dpf-operator-system get dpuservice,dpuserviceinterface,dpuservicechain
   ```

   If `hbn` or the SNAP examples run on the same DPUs, check that they and
   `cmx-target` do not share an uplink in separate chains (see
   "Decide where it runs" above).
